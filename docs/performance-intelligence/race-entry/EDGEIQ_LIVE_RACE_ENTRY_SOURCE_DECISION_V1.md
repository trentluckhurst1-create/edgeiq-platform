## Selected Source Architecture

The repository already has a governed live-field architecture, but it is not currently populated with current/future runner declarations. The selected architecture is the existing three-day field/universe path:

```text
edgeiq_three_day_window_v1_common.py
-> build_edgeiq_three_day_window_v1.py
-> build_edgeiq_vic_three_day_meeting_calendar_v1.py
-> build_edgeiq_vic_three_day_meeting_universe.py
   reads race_card_report.csv, race_fields.csv, edgeiq_vic_live_fields_synced.csv, edgeiq_live_runner_board_v1.csv
   writes edgeiq_vic_three_day_meeting_universe.csv and edgeiq_vic_three_day_race_fields.csv
-> build_edgeiq_three_day_product_catalog_v1.py
```

## Identity Strategy

When repaired, the existing universe builder provides deterministic keys from race date, normalised track, race number and normalised horse identity. Phase 5/6 must audit this before promotion into `edgeiq_race_entry_fact_v1.csv`.

## Known Gaps

- `edgeiq_three_day_window_v1.json` is stale relative to the audit date.
- `edgeiq_vic_three_day_race_fields.csv` is empty.
- `edgeiq_vic_three_day_meeting_universe.csv` is empty.
- Existing field sources are absent, stale, or off-calendar for July 23+.
- Racing.com race-list discovery exists, but it supplies race/form-entry names rather than full declarations with barrier, weight, jockey, trainer and scratching status.

## Decision

Do not build a duplicate ingestion layer yet. Repair/refresh the existing three-day field/universe path first. If the field source remains unavailable after deterministic repair attempts, classify the refresh as blocked and preserve valid historical PI outputs.
